# OMP automatic dashboard identification feasibility

Research date: 2026-09-15. Scope: OMP M1 V3 PRO and M2 V3 SPORT using OFS3(+) with ExpressLRS/CRSF. This note records the source evidence and the OMP Auto implementation contract. It does not certify radio behavior.

## OMP and ExpressLRS evidence

**Confirmed:** M1 V3 PRO uses a 2S 400 mAh LiHV battery and OFS3+ with integrated ExpressLRS. OMP sells the M2 V3 SPORT replacement battery as 3S 850 mAh LiHV. These establish the two battery classes, not each owner's fitted battery capacity. Sources: [M1 V3 PRO product specification](https://www.omphobby.com/OMPHOBBY-M1-V3-PRO-3D-RC-Helicopter-p4692196.html), [M2 V3 SPORT battery specification](https://www.omphobby.com/OMPHOBBY-M2-V3-PRO-M2-V3-SPORT-11-4V-3S-850mAh-60C-HV-LiPo-Battery-OSHM2514-p4764308.html).

**Confirmed from [OFS3 User Guide R6, v260718D](https://drive.google.com/file/d/1TPYRaM7gUR5QHPxwkQfL9VeC_qGgN9_B/view):**

| Topic | Documented behavior |
| --- | --- |
| CRSF voltage, p29 | `RxBt` is total pack voltage; `Volt` is average cell voltage: `RxBt/2` for M1, `RxBt/3` for M2. |
| Other CRSF fields, p29 | Current, consumed capacity, RPM, ESC temperature, attitude and remaining battery percentage. No `Cels`, `Vcel`, aircraft name or unique aircraft identifier is listed. |
| Sensor versions, p29 | Direct `Volt`, RPM and temperature support requires ExpressLRS 3.5.5+ and EdgeTX 2.11.2+. The earliest OFS3 version supplying `Volt` is not specified here. |
| Shared radio model, p30 | OMP explicitly supports one model memory for all OFS3(+) aircraft. Its supplied model file requires OFS3 17.17+, EdgeTX 2.11.2+, ExpressLRS 3.5.6+. |
| Receiver target, p24 | The documented integrated receiver target is generic: OMPHOBBY OFS3+ 2.4 GHz RX. |
| Protocol distinction, p37 | F.Port `RxBt` means receiver supply voltage; pack voltage is `EscV`. CRSF assumptions must not be applied to F.Port. |

The PDF is linked by OMP's [official manual page](https://www.omphobby.com/User-Manual-n2050698.html). Download SHA-256: `5cae19c1fc724f6fc78a6de3c4ae2802590a8e1c2bda84437d970149f6e8b211`. Its printed page numbers identify the evidence above. OMP's [radio files page](https://www.omphobby.com/Radio-Files-n2057525.html) provides the corresponding shared model files. No OFS3 setting changing CRSF `RxBt` to per-cell voltage was found in R6; modified radio sensor scaling remains a separate possibility.

**Confirmed:** ExpressLRS can bind multiple receivers to the same binding phrase. Model Match checks a receiver's configured model number against the selected radio receiver number; it does not automatically select a radio model. Sharing a radio model consequently requires compatible binding/model-match settings and control-channel configuration. [ExpressLRS Model Matching](https://www.expresslrs.org/software/model-config-match/).

**Confirmed code boundary:** ExpressLRS 3.5.6, commit `ee188b4efb9a707f682e8b2d966cd670de92ab50`, supports battery and cell frames as separate types (`0x08`, `0x0E`). Its device-information packet copies the firmware device name and uses the constant `ELRS` marker as its serial number. That packet is not a unique helicopter identity. Sources: [frame types](https://github.com/ExpressLRS/ExpressLRS/blob/ee188b4efb9a707f682e8b2d966cd670de92ab50/src/lib/CrsfProtocol/crsf_protocol.h#L55-L74), [device-information construction](https://github.com/ExpressLRS/ExpressLRS/blob/ee188b4efb9a707f682e8b2d966cd670de92ab50/src/lib/Handset/CRSF.cpp#L65-L77), [firmware device-name initialization](https://github.com/ExpressLRS/ExpressLRS/blob/ee188b4efb9a707f682e8b2d966cd670de92ab50/src/lib/OPTIONS/options.cpp#L373-L399).

## Feasibility inference and boundaries

For these two known aircraft, `RxBt / Volt` near 2 or 3 is a strong basis for choosing a configured M1 or M2 dashboard profile. Examples: `8.4 / 4.2 = 2`; `12.6 / 4.2 = 3`. It uses the FC's documented per-cell calculation and remains applicable to partly discharged batteries. This is cell-class recognition, not discovery of a unique FC name: every supported 3S M2 would look alike, as would two M1s. Display labels and image paths must be supplied locally.

A robust implementation should require both correct CRSF sources, valid fresh readings, a live link, plausible positive values and a stable near-integer ratio before selecting. Separate frames can have different sample ages, so one instantaneous quotient should not switch profiles. Establish identity on the ground, retain it during flight, and revalidate across a confirmed new connection. Missing, stale or contradictory data should remain unresolved or use explicit manual selection. Do not silently fall back to raw-voltage guessing.

Pack voltage alone is a weaker heuristic: it relies on expected battery condition and unmodified sensor scaling. It provides no unique identity and can be confused by abnormal voltage or stale telemetry. `Volt` is a calculated average, not measurements of individual cells; the quotient validates the configured battery class, not cell health or the physically connected pack independently.

**Unknown until radio verification:** the user's OFS3 and EdgeTX versions (the user reports ExpressLRS 4.1); discovery and exact identifiers of `Volt`; offsets/ratios/renamed or calculated sensors; update timing; and any undocumented OMP FC device-name response. Public OMP documentation reviewed here establishes no native unique-aircraft telemetry contract. No real-radio capture or flight validation was performed.

## Baseline KSE behavior and EdgeTX APIs

Local baseline: `c3cc1362a5e3493c7c68e5a11a88b1394f377153`. Both generated dashboards use the same authored telemetry code. At that baseline, the [OMP sensor map and cell helpers](../src/shared/telemetry.lua) read `RxBt`, ignored `Volt`, inferred 3S from an `M2` name match or 2S from `M1`, and derived average cell voltage by division. The M1 branch also selected LiHV chemistry. Manual OMP retains that behavior; the automatic extension belongs in the shared engine.

Existing [model-name selection](../src/shared/telemetry.lua), [image lookup](../src/shared/images.lua) and [flight-counter identity](../src/shared/counters.lua) already share `getModelName()`. The existing [Auto Elec/Nitro feature](../src/shared/auto_heli.lua) supplies a confirmed Rotorflight name to that path without renaming the saved radio model. It is currently Rotorflight-only and must not be fed OMP labels through its Electric/Nitro inference. An OMP identity provider could reuse the display/image/count paths while keeping OMP telemetry and its local counter.

EdgeTX 2.12.4, commit `def35ad324896b45d6607d4778536b1bc5360d20`, independently confirms the required API behavior:

- [CRSF sensor definitions](https://github.com/EdgeTX/edgetx/blob/def35ad324896b45d6607d4778536b1bc5360d20/radio/src/telemetry/crossfire.cpp#L59-L80) and [voltage-array decoding](https://github.com/EdgeTX/edgetx/blob/def35ad324896b45d6607d4778536b1bc5360d20/radio/src/telemetry/crossfire.cpp#L274-L295) expose scalar voltage telemetry. Do not treat OMP `Volt` as a `Cels` array.
- [getSourceValue](https://github.com/EdgeTX/edgetx/blob/def35ad324896b45d6607d4778536b1bc5360d20/radio/src/lua/api_general.cpp#L777-L840) returns value/current/fresh evidence. These flags and source identity checks should qualify both readings. Stable elapsed time is useful because repeated widget reads do not necessarily represent newly received packets.
- [Source lookup](https://github.com/EdgeTX/edgetx/blob/def35ad324896b45d6607d4778536b1bc5360d20/radio/src/lua/api_general.cpp#L414-L529) exposes the `telem1` base and three source IDs per sensor slot. [model.getSensor](https://github.com/EdgeTX/edgetx/blob/def35ad324896b45d6607d4778536b1bc5360d20/radio/src/lua/api_model.cpp#L1721-L1772) provides custom/calculated type, name, unit, raw ID and instance. In-range empty slots return tables; out-of-range slots return nil. [RPM decoding](https://github.com/EdgeTX/edgetx/blob/def35ad324896b45d6607d4778536b1bc5360d20/radio/src/telemetry/crossfire.cpp#L244-L272) adds the sensor ID in the upper byte of the RPM identifier.
- [model.setInfo](https://github.com/EdgeTX/edgetx/blob/def35ad324896b45d6607d4778536b1bc5360d20/radio/src/lua/api_model.cpp#L83-L121) supports changing only `name`, leaves omitted fields unchanged, and marks the model for storage. Actual radio-model renaming is possible, but is unnecessary for KSE title, image and count selection. If requested, perform it only on a confirmed identity change and respect the radio's name length.

## OMP Auto implementation contract

These source conventions also hold in the compiler-test baseline, EdgeTX v2.12.1 `1511b3f29152f18c704f1f89b3608e0f71317de9`: [source indexing](https://github.com/EdgeTX/edgetx/blob/1511b3f29152f18c704f1f89b3608e0f71317de9/radio/src/lua/api_general.cpp#L475-L508), [sensor metadata](https://github.com/EdgeTX/edgetx/blob/1511b3f29152f18c704f1f89b3608e0f71317de9/radio/src/lua/api_model.cpp#L1746-L1763), and [native RPM/voltage decoding](https://github.com/EdgeTX/edgetx/blob/1511b3f29152f18c704f1f89b3608e0f71317de9/radio/src/telemetry/crossfire.cpp#L248-L294).

Append **OMP Auto** as Heli Type choice 5, preserving the ten saved option slots, manual OMP choice 3 and Rotorflight Auto Elec/Nitro choice 4. Its effective type remains OMPHOBBY and its effective counter remains KSE Counter, without changing the saved counter preference. Confirm `RxBt / Volt` near 2 or 3 and use the fixed names **OMP M1** and **OMP M2** for title, image lookup and separate local flight histories. The saved EdgeTX model name is arbitrary and is never changed; `OMP Helis` is an example. Existing counts under those exact keys are reused; other history is neither merged nor migrated.

The shared [identity module](../src/shared/omp_auto.lua) samples at 10 Hz, before layout and counting, and requires 50 ticks of consistent ground evidence. Both voltages and stopped RPM must be current/fresh, with a live RSSI link. Require average cell voltage from 2.0 to 4.5 V and a quotient within 0.15 of 2 or 3. Ground proof is exactly zero RPM; missing, stale, negative or running RPM cannot establish a new identity. This RPM requirement belongs only to OMP identification, not MSP admission.

Resolve source slots afresh for identity samples. Require unique, custom (not calculated) sensors named `RxBt`, `Volt` and `RPM`, with voltage/RPM units and instance 0. `RxBt` has raw ID `0x08`; `Volt` has low byte `0xFE` and high byte at least `0x80`; RPM has low byte `0x0C`. Track all three source slots throughout confirmation. A bounded metadata scan checks duplicate names at acquisition start and completion; steady flight does not scan slots or read `Volt`. User voltage scaling/offset is not exposed by the Lua metadata API and must retain its original sensor settings.

Retain manual name-based OMP operation for installations lacking `Volt`. Initial automatic selection displays `OMP AUTO`; missing or contradictory evidence must not fall back to the transmitter name or raw-voltage guessing. An already confirmed name/image survives a telemetry gap. An observed disconnect requires reconfirmation once fresh stopped RPM returns; a different ground ratio or changed source slots also requires new confirmation. Suppress count display and attribution while unresolved, and clear timer qualification so a threshold crossed while unresolved is not credited after reconfirmation. Keep ordinary valid telemetry available.

A brief link loss, same-class reconfirmation or theme update must preserve warning latches and extrema. A confirmed class change on the ground resets battery chemistry, extrema, smoothing, motor-alert evidence and timer qualification. Saved model filename changes and manual/automatic option changes require a fresh identity/session; a radio display-name edit does not. M1 keeps deterministic LiHV behavior. M2 retains existing high-voltage chemistry detection, supporting other M2 packs rather than treating cell count alone as chemistry proof. Clear frame caches when the counter changes aircraft identity, because layout may have sampled cells before the session reset clears validity flags.

This reads telemetry already broadcast by the FC: no additional MSP requests, device probes, RF Tool changes or extra runtime Lua files are needed. Apply the existing EdgeTX compiler/resource gates and both-dashboard behavior tests to changes in this path. Compiled size and mocked instruction counts establish only their measured scope; retained memory and complete callback timing still require radio measurements.

The reproducible [OMP Auto fixtures](../tests/omp_auto/README.md) exercise these boundaries in both generated dashboards at all three screen sizes. Run them with the existing behavior, Rotorflight Auto, MSP, ownership, rendering and compiler/resource gates. Radio acceptance must additionally cover both aircraft with full and partly used packs; actual source update timing; discovery while connected; cross-aircraft reconnection; a brief in-flight dropout; separate pictures/counts; and manual OMP behavior. Verify the actual shared transmitter model's channel mapping, throttle/collective configuration, binding and Model Match on both helicopters. OMP's supplied shared model proves this workflow is supported; it does not validate an arbitrary existing transmitter file. OMP's software-throttle feature can store separate RPM presets in each FC (R6 p49) when required.
